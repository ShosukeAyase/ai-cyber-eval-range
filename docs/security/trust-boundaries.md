# Trust Boundaries

## TB-1: Human/operator to control plane

- Authentication: phishing-resistant MFA and managed workstation.
- Authorization: role and engagement-based.
- Controls: signed submissions, dual approval for policy/scope changes, session recording for break-glass.

## TB-2: Model Gateway to model provider

- Only redacted, minimum-necessary context leaves the control plane.
- No credentials, raw secrets, unrestricted network topology, or mutable authorization data.
- Model responses are untrusted and must be parsed against strict schemas.

## TB-3: Control plane to execution plane

- One-time job grants, mutual workload identity, explicit audience, short expiry, anti-replay nonce.
- No standing administrative channel from runners to the control plane.
- Policy is re-evaluated at execution time.

## TB-4: Execution plane to cyber range

- Destination tuples are generated by trusted resolvers from target IDs.
- Egress is default deny; only scenario-local routes exist.
- Range services are hostile and cannot authenticate to control services.

## TB-5: Execution/range to observability plane

- Write-only telemetry gateway or one-way transfer where feasible.
- Separate keys and administration.
- Execution identities cannot query, update, or delete retained evidence.

## TB-6: Supply chain to build/staging

- Imported artifacts enter quarantine.
- Hash, signature, provenance, license, malware, vulnerability, and policy checks precede promotion.
- No direct pull from public registries during an engagement.

## Separation requirements

No plane shares IAM roots, credential stores, network namespaces, host kernels for high-risk jobs, encryption keys, or audit administrators. Development convenience does not override this requirement.
